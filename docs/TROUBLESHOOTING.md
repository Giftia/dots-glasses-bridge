# 故障排查

先确认失败在哪一段：眼镜工具调用、桥接保存、原 Dot 事件与读取、回复回传、微信上游接受、手机显示。各段状态分别判断。不要把“已入队”“HTTP 200”“有效订阅”或“已保存回复”当成整条链路成功。

| 现象 | 先检查 | 处理 |
| --- | --- | --- |
| 眼镜工具为零或 401 | MCP 地址和眼镜 Bearer | 使用 `/dots/glasses/mcp`；不要重复 `/mcp`，不要混用 OAuth 或微信凭据 |
| 原 Dot 连接或授权失败 | HTTPS、根目录 OAuth 元数据、连接口令与权限 | 对照 [DEPLOY](DEPLOY.md) 和 [DOT](DOT.md)，不能用口令摘要登录 |
| 一直 `queued` / `notified` | 原生 Events 权限、有效订阅、回调挑战、Dot 是否调用读取工具 | 按事件链逐段核对；恢复后明确查待办，不假定历史自动重放 |
| 图文链接没有或过期 | 当轮是否有真实附件、附件剩余有效期 | 纯文本没有图文入口；附件仍有效时重新查询，附件过期则让 Dot 重新提供 |
| 微信没有手机通知 | 登录绑定、本人上下文、单一消费者和持久化回执 | 按下面步骤只读确认；接口接受后仍需手机验收 |

## 微信只读确认

下面均从源码目录执行；绝对路径仅为示例，替换为 [微信接入说明](WEIXIN.md) 中你实际使用的私有目录。不要把完整状态文件贴到 issue。

```sh
node tools/status-weixin.mjs /srv/dots-bridge/weixin-relay /srv/dots-bridge/weixin-channel
```

`ownerBound` 表示已经绑定本人，`contextReady` 表示保存了可用的本人上下文；它们都不是发送成功证明。`contextUpdatedAt` 是实际收到上下文的时间，不能直接换算为某个已证实的有效期。不要一边让 `watch-chat` 消费消息，一边运行手动 `context-check` 或另一个消费者争用同一账号。

## `ret=-2`、拒绝与发送不明

最近一次实际微信出站响应包含 `ret=-2`。当前唯一确认的是上游拒绝，具体语义未被证实；没有证据说明它必然表示上下文过期、固定时长限制、账号失效或必须重新扫码。

收到明确拒绝会保存 `rejected`；超时或无法判断是否送达会保存 `unknown`。相同通知编号再次提交只返回持久化回执，不盲目重发。双向 worker 的发送计划还会保存暂停状态，状态回执可能显示 `outbound_blocked`，同时继续处理本人入站消息。

1. 保留通道的 `weixin-channel.json`，以及 relay 的 `outbound-plan.json`、`cursor.json`、`receipt.json`；只提取状态、原因、时间与整数错误码供排查。
2. 确认只有一个账号消费者，并核对最近本人消息是否已进入当前安装；不要为碰运气重复扫码、重启多个 worker 或换通知编号。
3. 查明恢复条件后，才按 [受控恢复说明](WEIXIN-RECOVERY.md) 执行有明确目标和影响范围的人工恢复。显式重试仅适用于已确认拒绝的记录，`unknown` 继续暂停；先在手机核对是否已收到，避免重复发送。不要手工清空回执、删除发送计划或修改游标。

登录与扫码属于本人私有状态，登录过程和正常业务消费应分时进行。当前通道已绑定时，不能仅因 `ret=-2` 就断言需要解绑或重新绑定。重新启动 worker 本身不会解除已持久化的拒绝暂停。

## 启动与锁

事件回调出口与微信是独立检查。确实需要独立出口时，参见 [可选出口说明](WEBHOOK-EGRESS.md)；不要改全局代理或关闭证书验证来碰运气。

`RELAY_BUSY` 表示另一个 relay 仍持锁；先确认实际进程，再决定是否停止你管理的 worker。`STALE_RELAY_LOCK` 需要核对旧进程身份和状态目录，不能把报错当成删除整个私有目录的依据。服务只接受独立的本地监听和私有数据目录，不支持把旧安装目录直接拿来当新配置迁移。

提交问题时附上代码版本、Node 版本、运行模式、失败阶段、脱敏错误码以及 [验收清单](ACCEPTANCE.md) 的最后成功项。不要附二维码、token、连接口令、签名网址、真实聊天、照片或私有配置。
